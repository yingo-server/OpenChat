# 性能优化规范（v1.2 目标）

> 依据：v1.1.1 实测 + 独立架构评审 + 代码核实。
> 所有指标以 **2 核 4 GB** 为参考硬件。编译与测试一律走 CI，本地不做构建。

## 0. 已确证的现状（不要重新调研）

### 0.1 实测容量（CI，无限流，20 秒稳态，mixed 负载）

| 场景 | 成功消息/秒 | 服务端帧/秒 | 可用性(ACK/发送) | p50 / p95 |
|---|---|---|---|---|
| 512 连接 × 10 人群 | 3,535 | ~35,000 | 98.1% | 80 / 126 ms |
| 1000 连接 × 5 人群 | 4,498 | ~34,500 | 65.0% | 102 / 174 ms |
| 1000 连接 × 50 人群 | 2,196 | ~110,000 | 32.3% | 212 / 350 ms |
| 1000 连接 × 500 人群 | 150 | ~1,000,000(需求) | 2.2% | 1,642 / 4,227 ms |

### 0.2 两个独立瓶颈（这是全部优化的出发点）

**瓶颈 A：写路径 ≈ 5,000–6,000 消息/秒**
证据：512 连接×10 人（35k 帧，写入 3.5k/s）= 98%；1000 连接×5 人（34.5k 帧，写入 6.9k/s）= 65%。
**同样的帧量，写入翻倍 → 可用性掉 33 点。** 说明写路径先于扇出饱和。

**瓶颈 B：帧扇出 ≈ 40,000 帧/秒**
证据：1000 连接×50 人（110k 帧需求）= 32%；1000 连接×500 人（1M 帧需求）= 2.2%。
帧量每增加 3 倍，可用性掉约 3 倍。

**关键区分**：瓶颈 A 只在「高频小群」出现（每连接都在发）；瓶颈 B 只在「大群」出现（扇出宽度）。
500 人群 / 1000 在线 / 每人 0.5 msg/s 的场景：写入仅 500 条/秒（远低于 A），扇出 250,000 帧/秒（远超 B）。
**所以大群优化只需打 B。**

### 0.3 已核实的代码事实

| 事实 | 位置 | 含义 |
|---|---|---|
| 每成员重复序列化 | `server/cmd/chatd/wire.go` installEmit → 每帧 Encode 一次 | 500 人 = 500 次编码+拷贝，**最大单项浪费** |
| 无 writev 合批 | `acceptor.go` `c.ws.WriteMessage(mt, out)` 每帧一次 syscall | 可合批 |
| 队列无降级 | 4096/8192 有界队列，满了才丢 | p99 炸的元凶 |
| TCP_NODELAY | gorilla 默认已开 | **不需要优化，别浪费时间** |
| 上滑加载不请求服务端 | `bootstrap.ts` `historyLoader` 只查 IndexedDB | 历史永远拉不全（已修服务端，待前端） |
| 920 只有 sinceSeq | `wire.ReadHistory` | 已加 beforeSeq（已落盘，待验证） |

## 1. 模块 1：历史加载与滚动体验

### 1.1 服务端（已落盘，需验证）
- `wire.ReadHistory` 增加 `BeforeSeq uint64`（已加）
- 920 分支：`BeforeSeq > 0` → `ReadHot(cid, beforeSeq, limit, asc=false)`，**结果按 seq 升序返回**；`BeforeSeq == 0` 保持 `SinceSeq` 原语义
- kind 8（SYNC 补 gap）行为**不得改变**

### 1.2 前端三段式 loader
```
loadOlder(convId, beforeSeq, limit=50):
  1. 本地 IndexedDB 查 (convId, beforeSeq, limit)
     - 返回条数 >= limit  → 直接返回，不打网络
     - 本地已无更早数据   → 继续第 2 步
  2. 发 920 {convId, beforeSeq, limit}，await 921，超时 3s
     - 成功：写 IndexedDB → 返回
     - 超时/失败：返回本地已有的（不报错、不阻塞 UI）
  3. singleflight：同一 (convId, beforeSeq) 并发只发一次
```

### 1.3 滚动体验（硬指标）
| 要求 | 实现 | 验收 |
|---|---|---|
| 慢速上滑触发 | 距顶 < 200px | 到达前就开始加载 |
| **快速上滑预取** | 按 px/ms 动态放大阈值到 600–800px | 快速滑到顶时已有内容，无 loading 空窗 |
| **滚动锚定** | 插入前记录 `scrollHeight - scrollTop`，rAF 后恢复 | 插入旧消息后视口内容位移 = 0 |
| 不弹到底部 | 加载更早时**不得触发** scrollToIndex 到未读/最新 | 现有 unread 定位逻辑仍工作 |
| 取消过期 | convId 切换 → generation 比对，迟到响应丢弃 | 不写错会话 |
| 避免无用拉取 | `hasMore=false` → exhausted，永久停止请求 | 顶部显示"没有更多" |
| 请求上限 | 每次 50 条，同时最多 1 个在途 | 快速滑动不产生请求风暴 |

### 1.4 测试
前端：loader 三态（本地够/要网络/超时）、singleflight、exhausted、stale 丢弃、阈值纯函数、锚定补偿纯函数。
服务端：beforeSeq 方向、边界（不含 beforeSeq 本身）、hasMore、无权限 403。

## 2. 模块 2：扇出热路径（瓶颈 B）

### 2.1 序列化一次（最高优先，单项收益最大）
```
现状：for m in members { frame := buildEnvelope(msg); b := encode(frame); conn.Send(b) }
目标：b := encode(msg) once
      refs := 1 + len(members)
      for m in members { ring(m).push(b, refs) }   // 共享只读切片
      最后一个消费者释放
```
- payload 必须是**不可变**的；任何按连接定制（如 per-user 序号）必须在 encode **之前**完成，或改为 envelope 外层字段
- 引用计数泄漏会永久驻留内存 → 必须有生命周期单测

### 2.2 每连接 writev 合批
- 每连接一个 writer goroutine（已有），改为 `net.Buffers` + `WriteBuffers` 一次写出
- flush 策略：**队列清空即发 + 15ms 兜底**（空闲零延迟，高负载自动合批）
- **禁止**复用 100ms 瞬态聚合窗口——消息路径必须独立
- TLS 注意：`*tls.Conn` 下 `net.Buffers` 不保证合并成单 record，需实测确认收益还在

### 2.3 有界环 + 慢消费者降级
- 每连接队列容量降到 1024（当前 4096/8192）
- 满了**不丢帧**，而是：标记该连接 lagging → 推一条 RESYNC 控制帧（带 latestSeq）→ 该连接转为拉取补齐 → 不再接收 inline 推送
- 目的：**单个慢客户端不得拖慢整组扇出**；这是 P95 从"随负载增长"变成"常数"的关键

### 2.4 目标
| 阶段 | 2 核帧/s | 500人群×1000在线 可用性 |
|---|---|---|
| 现状 | 40,000 | 2.2% |
| 2.1 完成 | 80,000–120,000 | ~10% |
| 2.1+2.2 | 150,000–250,000 | ~40–60% |
| +2.3 | 同上但 **P95 ≤100ms 且 p99≈p95** | 抖动消除 |

## 3. 模块 3：写路径（瓶颈 A）

| 手段 | 预期 | 风险 |
|---|---|---|
| 多值 INSERT（一条 SQL 插 N 行） | 2–3x | 需处理 SQLite 变量上限（默认 999） |
| 组提交批 1000→2000，间隔 50ms 不变 | 1.5x | 内存占用上升 |
| `PRAGMA synchronous=NORMAL`（已开）、`wal_autocheckpoint` 调优 | 1.2x | 掉电丢最近事务（已有文档说明） |
| 可选：异步刷盘（内存队列 + 后台写，先 ACK 后落库） | 3–5x | **牺牲持久性，默认关闭，仅限可丢消息场景** |

目标：6,000 → 15,000–20,000 消息/秒。

## 4. 模块 4：大群拉取模式（治本）

### 4.1 阈值切换
```
len(members) <= N (建议 100):  inline push（模块 2 优化后）
len(members) >  N:             推 20 字节水位线 {convId, seqHi} → 客户端批量拉 920
```

### 4.2 客户端
- 收到水位线 → 若本地 lastSeq < seqHi → 发 920（beforeSeq 不用，用 sinceSeq 拉增量）
- 合流：同一 conv 的并发拉取去重（singleflight），避免惊群
- 拉回后按现有 sync engine 写入（seq 校验、gap 缓冲、tombstone）

### 4.3 预期
500 人群 / 1000 在线 / 0.5 msg/s：
- 写入侧：500 msg/s（无变化）
- 下行：500 条水位线/s（而非 250,000 帧/s）
- 拉取侧：每个在线用户每秒最多 1 次 920（受合流保护）
- **2 核可支撑，P95 ≤100ms**

## 5. 模块 5：压测与验收

| 指标 | 门槛 |
|---|---|
| 500人群 × 1000在线 × 0.5 msg/s | 可用性 ≥95%，P95 ≤100ms，p99 ≤200ms |
| 50人群 × 1000在线 | 可用性 ≥95%，P95 ≤100ms |
| 10人群 × 512在线 | 可用性 ≥99%，P95 ≤80ms（不得低于 v1.1.1） |
| 5人群 × 1000连接 | 可用性 ≥95%（写路径优化后） |
| 抖动 | p99/p95 ≤ 2.0 |

压测必须带 `--conv-members` 与 `-no-ratelimit`（原始容量），并在报告中标注。

## 6. 明确不做（避免浪费）

- ❌ 按成员 ID 尾号分批（不减少工作量，天花板=核数）
- ❌ 优化 WS 帧头 / 小帧压缩（负优化）
- ❌ 合并"发给不同 socket"的帧（物理不可能）
- ❌ 把消息塞进 100ms 瞬态聚合窗口（P95 直接爆）
- ❌ TCP_NODELAY（已默认开启）
- ❌ 无界大队列当缓冲（把丢帧换成 3s 尾延迟）

## 7. 执行顺序（依赖关系）

```
模块1（历史加载）  ──┐
                    ├─→ 模块4（大群拉取，复用 920）
模块2（扇出热路径）─┘
模块3（写路径）    ──→ 独立，可与 2 并行
模块5（压测）      ──→ 必须最后，验证 1+2+3+4
```

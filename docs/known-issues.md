# OpenChat 1.1 已知问题

> 版本：1.1.0（LTS 基线）
> 每条都在「现象 / 影响 / 计划版本」三栏里说明。已修复项移至 `CHANGELOG.md`。

## 部署与依赖

### 1. 冷库 Postgres driver 需部署层注册

**现象**：`chatd` 按架构约定不 import 任何 PostgreSQL driver。`cold_dsn` 非空时
执行 `sql.Open("postgres", dsn)`；若部署层未注册驱动，启动日志报
`cold store disabled: driver not registered`，冷库句柄为 nil。

**影响**：历史归档与冷读不可用；**审计事件降级为只写日志不落盘**（每次打 WARN，
`Dropped` 计数增长）。合规部署不可接受此状态——请设 `require_audit_store=true`
让它在冷库不可用时直接拒绝启动。

**计划版本**：v1.2 提供带驱动的构建变体与启动自检。

### 2. 短信 / 邮件 / 图形验证码供应商未接入

**现象**：`SMSSender`、`Mailer`、`CaptchaVerifier` 只有接口与 `dev` 实现。
`APP_ENV=dev` 时验证码固定、魔法链接直接回包、图形码任意非空值通过。

**影响**：生产环境手机/邮箱注册登录不可用；第 2 条 OTP 起强制图形码（未配则 fail-closed
拒绝，这是有意行为）。

**计划版本**：v1.2 接入供应商适配器。

### 3. Windows ARM / ARM64 不提供构建产物

**现象**：发布包覆盖 Linux（x86_64 / x86 / arm64 / armv7 / riscv64，均静态链接 SQLite）
与 Windows（x86_64 / x86）。**Windows on ARM 与 ARM64 没有产物**——这两条目标没有可用的
mingw CGO 工具链（SQLite 需要 cgo），CI 显式标记为不支持而不是静默跳过。

**影响**：Windows ARM 机器需要自行编译（装 mingw + Go，`GOOS=windows GOARCH=arm64
CGO_ENABLED=1` 且需 arm64 mingw 工具链），或改用 x86_64 版本走模拟。

**计划版本**：视需求（若改用纯 Go 的 SQLite 驱动则可全平台无 cgo 交叉编译）。

### 4. split 多进程部署未实现

**现象**：`deploy/systemd/openchat-{bridge,user,data,admin}.service` 是 v1.2 的预留，
`ExecStart` 指向当前构建不产出的二进制；`chatd` 目前只支持 embedded 单进程。

**影响**：不能把一个部署拆到多台机器上做水平扩展。单机 2C2G 场景不受影响。

**计划版本**：v1.2。

## 功能边界

### 5. 群通话 / 屏幕共享未实现

**现象**：通话只支持 1 对 1。群聊里的通话按钮禁用并提示"群通话暂不支持"。

**影响**：群内无法开会。1v1 通话功能完整（含忙线、超时、ICE 失败处理）。

**计划版本**：v1.2 接云 SFU（LiveKit/Twilio）过渡，不自建。

### 6. 移动端无推送

**现象**：只有 Web 端，没有 PWA service worker 与推送通道。

**影响**：**手机锁屏时收不到消息**——移动端实际上不可用。这是与主流 IM 差距最大的一项。

**计划版本**：v1.2（PWA + Web Push / 厂商通道）。

### 7. 通话需要自备 TURN 服务器

**现象**：客户端默认只配公共 STUN。对称 NAT 环境下（约 10% 用户）无法直连。

**影响**：这部分用户通话建不起来。`deploy/coturn/turnserver.conf` 提供了硬化模板。

**计划版本**：保持自备（TURN 涉及带宽成本，由部署方决定），v1.2 在管理界面加一键测试。

### 8. 群人数上限（默认 100，硬上限 1000）

**现象**：`group.max_members` 默认 **100**（v1.1 起），代码硬上限 1000（64KB 帧约束）。

**影响（实测，务必按此规划）**：群越大，每条消息的扇出帧越多。2 核机器帧扇出上限约 4 万/秒：

| 群成员 | 1000 并发连接下的可用性 |
|---|---|
| 10 | 98% |
| 50 | 32% |
| 500 | **2.2%（基本不可用）** |

所以虽然技术上允许 1000 人，**2 核机器上超过 50-100 人的活跃群就会明显劣化**。默认值 100 是按 2 核预算取的保守值；调大前请按「在线人数 × 群成员数 × 每人消息频率 ≈ 帧/秒」核算，不超过 4 万帧/秒（8 核可到约 16 万）。

**计划版本**：v1.2 提供大群拉取模式（消息不逐成员扇出，客户端按 seq 主动拉取），届时上限可进一步放大。

### 9. 消息编辑 / 转发 / @提及 服务端未实现

**现象**：`MSG_EDIT(106)` 前端有渲染，服务端没有编辑处理；转发与 @提及的协议字段在，
没有业务实现。

**影响**：只能发新消息，不能改、不能转、@ 不会提醒。

**计划版本**：v1.2。

### 10. 会话列表未虚拟滚动

**现象**：`ConvList.tsx` 直接 map 渲染，只做了行级 memo；消息列表已虚拟滚动。

**影响**：会话数上千时首屏 DOM 偏多。功能正常。

**计划版本**：v1.2。

## 运维注意

### 11. 升级到 v1.1 必须做一次热库 auto_vacuum 转换

**现象**：新库自动启用 `auto_vacuum=INCREMENTAL`；**已有库不会自动转换**。

**影响**：不转换则删除的行不会归还磁盘，热库只涨不落。

**处理**：按 `docs/deploy.md §7.4` 执行一次（停服 → 备份 → `PRAGMA auto_vacuum=INCREMENTAL; VACUUM;` → 校验返回 2）。

**计划版本**：不需修复，属一次性升级动作（启动时会对 `auto_vacuum=0` 的库打 WARN）。

### 12. 旧版 `thumb_data` 需要手工迁移

**现象**：v1.1 之前缩略图存在数据库的 `thumb_data` 列（约 10.7KB/行）。
v1.1 起写入文件系统，但存量行不会自动搬。

**影响**：数据库里仍占着这部分体积（读取会回退到旧列，功能不受影响）。

**处理**：`openchatctl migrate thumbs --dry-run` 先看规模，再 `--run`。

**计划版本**：已提供工具；v1.2 在升级流程里自动化。

## 容量：扇出写放大是主要约束

一条消息发给 N 个成员就要写 N 次。**2 核机器上帧扇出吞吐上限约 40,000 帧/秒**（实测）：

| 场景 | 帧/秒 | 可用性(ACK/发送) | 端到端 p50/p95 |
|---|---|---|---|
| 512 连接 × 10 人群 | ~35,000 | 98.1% | 80 / 126 ms |
| **1000 连接 × 50 人群** | ~110,000 | **32.3%** | 212 / 350 ms |
| **1000 连接 × 500 人群** | ~1,000,000(需求) | **2.2%** | 1,642 / 4,227 ms |

**1000 个并发连接本身没问题**（两次测试握手均 1000/1000 成功）。超限后不是崩溃，是排队变长 + 服务端 NACK（压测报表 `srv_drop` 列）。

这不是缺陷而是群聊的固有成本。容量规划按「在线人数 × 群成员数 × 每人消息频率」估算帧扇出总量，压到 40k 帧/秒以内。**大群（>100 人）在 2 核机器上不可行**，需 8 核以上或等 v1.2 的大群拉取模式（消息不扇出、客户端按 seq 拉取）。

缓解手段（按代价排序）：按群规模拆分实例、提高群成员上限时同步加核、对超大群改用「拉模式」（客户端按 seq 拉取而非服务端推送）。
